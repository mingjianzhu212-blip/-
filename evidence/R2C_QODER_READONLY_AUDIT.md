## 逐项结论

### 1. bagCap 是否可被构造函数 / 特殊路径绕过

- **是否存在风险：正常玩法否；存档 / 调试面是（部分）**
- **代码位置**：`bagCap` 5937、`bagMaxCap` 5939-5942、`addItem` 5944-5952；所有直接写包路径 2513、2573、6943、6949、7086、8538、10643；读档钳制 3951、4195-4203、4317
- **风险等级：低**
- **证据**：
  - `function bagCap(){ return S.bagSize + dtBagN(); }`（5937）；`bagSize` 读档被夹到 `[BAG_BASE, BAG_CAP]`（4317），`S.dt` 每座洞天被夹到 `0..DT_MAX`（4198-4199），所以容量上限不可通过改档放大。
  - 所有直接 `S.bag.push(...)` 的路径都带 `S.bag.length < bagCap()` 判断（2512、2572、6942、6948、7085、10642）。
  - 唯一无容量判断的是**转世回收装备**（8538），但这是设计明示的有意超容：`故不做容量判断——宁可超容也不丢`（8513）。读档也为它留了 `bagMaxCap() + EQUIP_SLOTS.length` 的余量（4341）。
  - 真正的"越权"只存在于存档编辑/控制台：`_s: S` 直接把可变的真实存档对象挂到调试接口（11841），任何同页脚本可 `XX._s.bag.push(...)`。
- **结论**：常规玩法未发现可绕过 50（+洞天加格）容量的路径；不存在"买一次扩容多次生效"的漏洞（见第 7 项）。

### 2. addItem 是否有重复入库、负数量、NaN / undefined 防御

- **是否存在风险：是（无防御），但当前调用方均为内部可信数据**
- **代码位置**：5944-5952；忽略返回值处 1973-1974、2344、5750、6590、8413-8415
- **风险等级：低**
- **证据**：
  - 实现仅四行：容量判断 → `S.bag.push({ t, n })` → `renderBag()`，**不校验 `t` 是否在 `ITEMS` 表中、不校验 `n` 类型、不合并同类项、没有幂等键**。
  - 该函数的第二参数 `n` 实际是"显示名"（如 `addItem('dan1','下品破境丹')`），不是数量；因此不存在"负数量"语义，但也意味着任何 `undefined/对象型 n` 会原样存盘。
  - 多处调用不检查返回值：签到奖励（1973-1974）、任务奖励（8413-8415）、论剑兑换（2344）、坊市（5750）、炼制产物（6590）。背包满时 `addItem` 返回 `false`，这些路径会**静默吞奖**（签到/任务仍会推进天数或标记完成），属于玩家资产损失而非刷取。
- **结论**：无重复入库的真实业务路径；缺少输入白名单与失败处理，属于健壮性缺口。

### 3. removeItems 数量不足时是否静默通过（导致资产变负）

- **是否存在风险：部分（静默，但不会变负）**
- **代码位置**：`removeItems` 6397-6400、`matTake` 6430；前置校验 1652、4907、6460-6463、6554-6558、2971-2973
- **风险等级：低**
- **证据**：
  - `removeItems` 用 `filter` 最多删到实际持有数，**没有返回值、没有"删除不足"的报错**：`if(x.t === t && removed < n){ removed++; return false; }`（6399）。
  - 背包物品按"一件一条"存储，不会出现负数；但计数器材料走 `matTake` 的裸减法：`S[MAT_COUNTERS[t]] -= n`（6430），若调用方不前置校验就会**把计数器扣成负数**。
  - 我核对了当前全部调用点：强化（1652-1656）、突破丹药（4907/5000）、建筑升级（6460-6466）、炼制（6554-6563）、洞天（2971-2976）都先 `matHas/countItem` 校验；且 `RECIPES`、`DAN_VARIANTS`、`DONGTIAN[].mats` 中每个材料项都是唯一的，不存在"同一材料写两次"导致校验通过而双扣成负的情况。
- **结论**：当前无负资产路径；`removeItems / matTake` 缺少失败信号，是潜在的防御性缺陷。

### 4. craftItem 材料扣减与产物发放是否原子

- **是否存在风险：部分（无事务/回滚；但正常流程不会白嫖）**
- **代码位置**：`craftItem` 6531-6614；容量预检 6560；扣款 6562-6563；判定 6574-6575；发奖 6576-6593；失败返还 6595-6607
- **风险等级：低**
- **证据**：
  - 顺序是"校验 → 扣灵石/材料 → 掷成功 → 发产物 → `save()`"（6560→6562→6575→6590→6613），**先付后给**，因此正常异常路径只会"扣了没给"，不会出现"没扣却给了"。
  - 没有任何 `try/catch` 和事务回滚：若 `S.recipeN` 写入、`Math.random`（6575，可被控制台替换）或后续 UI 代码抛错，内存中材料已被扣，磁盘因 `save()` 未执行而暂时旧档，下一次自动存档会把"材料已扣"落盘。
  - 容量预检只覆盖非武器产物（6560）；武器/法器直接写 `S.weapon / S.art`，不占背包，属正常设计。`addItem` 的返回值在 6590 未检查，但因 6560 预检，正常单线程下不会失败。
- **结论**：不存在"白嫖产物"的真实顺序漏洞；原子性不足，异常时可能丢材料。

### 5. eatItem 属性加成是否有上限 / 溢出

- **是否存在风险：否（正常玩法有钳制）**
- **代码位置**：`eatItem` 6660-6698、`eatDan` 6642-6658、`danTake` 5217-5222、`pillBonus` 3664、`breakChanceWith` 4803-4815、`attemptBreakthrough` 4930-4934、`danClean` 5202-5215
- **风险等级：信息**
- **证据**：
  - 丹药加成来自固定表 `DAN_FX`（785-790），每种丹药只覆盖本族一个槽：`S.danExp/S.danPow/S.danGain = {...}`（5219-5221），**不叠加层数**。
  - 破境丹加成最终被夹在硬上限：`Math.min(BAL.breakMax, ...)`（4933），`breakMax: 0.95`（321），单次判定最高 95%。
  - 淬体 / 聚灵 / 丰产三族 buff 在 `danClean` 里读档时被夹到 `[0,5]`（5204-5214），不会因改档变成无限倍率。
  - 唯一没有上限的是 `S.pillBonus / S.pillUntil` 的读档（3940-3942 仅 `>=0`）：恶意档可写入极远未来时间戳获得"永久 buff"，但突破概率仍被 0.95 封顶；属于存档编辑面，不是玩法漏洞。
  - `S.exp += expRate() * d.exp`（6649）没有上限，但修为本身是消耗型资源，不是可兑换资产。
- **结论**：正常路径无溢出/叠层漏洞。

### 6. equipItem / unequipItem 装备槽位是否可能越界

- **是否存在风险：否（槽位本身）；但存在"换装丢件"副作用**
- **代码位置**：5961-5991（穿）、5993-6012（卸）、4010-4013（读档校验）
- **风险等级：低（越界）；中（换装丢件）**
- **证据**：
  - 穿前校验 `!meta.slot || EQUIP_SLOTS.indexOf(meta.slot) < 0`（5963）；卸前 `EQUIP_SLOTS.indexOf(slot) < 0`（5994）；读档只接受 `ITEMS[id].slot === k`（4012）。槽位不可能越界或跨槽。
  - **但 `equipItem` 先 `S.bag.splice(idx,1)`（5974）再 `addItem(oldId,...)`（5977）**。若背包已经超容（合法可达：转世把最多 3 件装备塞回满包，8513-8539；或改奉主洞导致容量变小），`splice` 后仍是 `length >= bagCap()`，`addItem` 返回 `false`，旧装备被直接丢失：`if(!returned) log('换下的旧装备背包放不下，已遗失。')`（5984）。
  - `unequipItem` 则是先 `addItem` 成功后才清槽（6002-6006），不会丢件，口径反而不一致。
- **结论**：槽位安全；换装路径在超容状态下会合法丢装备，是资产损失缺陷。

### 7. buyBag 购买是否真实校验货币扣除，会不会免费扩容

- **是否存在风险：否**
- **代码位置**：`buyBag` 6402-6411；其它扩容路径 2333-2337、5744-5759、8412（任务奖励）
- **风险等级：信息**
- **证据**：
  - `if(S.stone < cost){...return;}` → `S.stone -= cost` → `S.bagSize = Math.min(BAG_CAP, S.bagSize + BAG_STEP)`（6405-6407），扣款与扩容同函数同步完成。
  - 论剑声望兑换先扣声望（2336）再扩容（2337），坊市购买先扣灵石（5745）再扩容（5758）。
  - 免费扩容只有任务奖励 `if(r.bag) S.bagSize = ... + BAG_STEP`（8412），由 `claimQuest` 的一次性 `questsDone` 守卫（8417-8422），且总量 `Math.min(BAG_CAP,...)` 封顶；不是可重复白嫖。
- **结论**：正常购买路径不存在免费/重复扩容。

### 8. 存档序列化 / 反序列化篡改面：_parseSaveText 能否注入非法物品 / 数量

- **是否存在风险：是（部分校验）**
- **代码位置**：`parseSaveText` 11476-11497、`applySaveText` 11798-11832、`writeImportedSave` 11787-11797、`load` 背包清洗 4341、`save` 3860
- **风险等级：中（导入面持久 XSS）/ 低（物品伪造本身）**
- **证据**：
  - `_saveText` 只是 `JSON.stringify(S)`，**无签名、无校验和**（11881）。`save()` 直接 `localStorage.setItem(SAVE_KEY, JSON.stringify(S))`（3860），整份资产完全客户端可改。
  - `parseSaveText` 只验 `rank/exp` 与"至少 3 个特征字段"（11488-11493），**完全不检查 `bag` 数组**；`writeImportedSave` 把原始对象写回主键（11793），重载后由 `load` 处理。
  - `load` 的背包清洗是 `o.bag.filter(x => x && x.t && ITEMS[x.t]).slice(0, bagMaxCap()+3)`（4341）：
    - 能挡掉大部分未知 id，但 **`n`（显示名）原样保留、不转义**；`t` 也允许非字符串（数组等）。
    - 只按 `ITEMS[x.t]` 真值判断，原型链键可通过（见第 10 项）。
  - **持久 XSS 证据**：`n` 被直接拼进 HTML 属性与文本：`alt="' + it.n + '"'`（10956）、`'>' + it.n + '</span>'`（10959）、详情图 `alt="' + it.n + '"'`（6722）、坊市寄售行 `'<b>' + it.n + '</b>'`（5878）。项目本有 `escHTML`（3680）但这些背包渲染点未使用。导入一份恶意存档 → 重载 → 背包/坊市渲染时执行脚本。
  - `parseSaveText` 用 `k in o` 统计特征字段（11492），不是 `hasOwnProperty`；虽然当前特征键不在 `Object.prototype` 上，未发现直接绕过，但写法偏弱。
- **结论**：`bag` 内容是"浅过滤 + 无签名"，可注入非法/重复物品；`n` 未转义构成真实导入面 XSS。这是本次审计中安全影响最高的一项。

### 9. 背包物品数量是否强制整数，有无浮点注入

- **是否存在风险：否（背包条目）**
- **代码位置**：`S.bag` 结构 5949；`bagSize` 读档 3951/4317；计数器读档 3940-3942；`matTake/matGive` 6430-6435
- **风险等级：信息**
- **证据**：
  - 背包是"一件一条"的数组，没有数字数量字段；`S.bag.length` 天然是非负整数，读档 `slice` 后最大有限（4341），`bagSize` 被 `Math.floor` 夹入（3962/4317）。
  - `herb/ore/wisdom/...` 这类计数器允许小数（3940-3942 只取下限），但它们是资源计数，不进入背包条目；`matGive` 会 `Math.floor`（6432），`matTake` 直接减整数配方值，没有 `0.1+0.2` 造成多给/少给的路径。
  - `dtBagN` 由洞天整数等级 ×1.5 后再 `Math.round` 到两位（2909/2918），实际为整数。
- **结论**：无有效浮点注入面。

### 10. 物品 ID 是否可被伪造（非法 itemId 能否入库）

- **是否存在风险：部分（运行期 addItem 无白名单；读档真值判断可被原型键绕过）**
- **代码位置**：`addItem` 5944-5952；读档过滤 4341；`ITEMS` 普通对象字面量 5515；`SELL_K` 5691；`EATABLE` 6639；`DAN_BY_ID` 877；调试口 11841
- **风险等级：中（安全/不变量）/ 低（直接经济收益）**
- **证据**：
  - `addItem(t, n)` 不查 `ITEMS[t]`，任何内部调用误传 id 都会入库；当前所有调用点都来自常量表或 `ITEMS` 校验后的值，未发现外部可控入口。
  - 读档 `ITEMS[x.t]` 是**真值判断而非自有属性判断**：`t: "constructor"`、`"toString"`、`"__proto__"` 等会命中 `Object.prototype` 上的函数/对象而被保留（`ITEMS` 是普通对象字面量）；`t: ["dan1"]` 这类数组经属性键强制转换后也会命中原物品。结果是背包里出现 `t` 非字符串的"伪物品"，破坏 `countItem` 等按严格相等比较的逻辑。
  - 这些伪物品**不能卖成灵石**：`sellPrice` 里 `SELL_K["constructor"]` 得到函数，运算结果为 `NaN`，`if(!p)` 会拒绝（5780-5782）；`equipItem` 也因 `meta.slot` 不存在而拒绝。主要是可用性/不变量问题，不是直接刷钱。
  - 调试接口 `XX._s`（11841）直接暴露 `S`，可任意插入任意 id；`XX._applySaveText`（11885）也可导入任意 JSON。
- **结论**：运行期无外部可控的伪造入口；读档有原型链绕过与非字符串 `t` 的缺陷，建议改为 `Object.prototype.hasOwnProperty.call(ITEMS, t)` 且 `typeof t === 'string'`。

### 11. 联机 / 服务端对账逻辑中背包是否服务器权威

- **是否存在风险：是（背包完全客户端权威），但联机奖励流本身是服务器判定**
- **代码位置**：客户端快照 `multiSnapshot` 7288-7311、结算入账 7374-7407；服务端 `recomputePower` server.mjs 231-251、`settle` 674-715、`apiRunStrike` 1057-1069；服务端说明 190-213
- **风险等级：中（公平性）/ 信息（单机资产）**
- **证据**：
  - 服务端**完全没有背包 / 物品表**：全仓 grep `bag|inventory|item` 在 `server/server.mjs` 只命中 SSE 测试里的局部变量名；组队结算只下发灵石：`rewards`（server.mjs 674-700），客户端把石头发到自己存档：`S.stone += mine.stone`（7391）。
  - 客户端上报的是"受钳制养成快照"：`equipPower: equipPowerSum()`、`petPower: petPowerSum()` 都来自本地背包/装备/灵兽（7301-7302）。服务端按 `EQUIP_POWER_CAP = 4500`、`PET_POWER_CAP = 2160000` 等钳制（server.mjs 222-223、247-248），并忽略 `body.power`（server.mjs 190-213、799-822）。
  - 因此：**背包内容不参与服务器结算，也不被服务器校验**；改档可以把三槽装备、灵兽、境界、法宝等直接填到"合法满级"，在联机中获得被钳制后的满级战力。服务端注释已明确承认这一边界（server.mjs 190-213）。
  - `run_settle` 的 `runId` 有幂等表（multi-ledger.js、game.js 7385-7406），可防重复入账，但不校验客户端资产。
- **结论**：不存在"背包服务器权威"；单机资产无法防篡改，联机只保证"奖励金额/层数由服务器判定 + 客户端养成值上限钳制"。在当前"联机仅产出灵石、物品不跨玩家流通"的设计下，跨玩家资产风险有限，但公平性上限可被改档轻易触达。

## 补充发现（清单外，但属于资产/经济系统）

1. **详情页「寄售」与坊市是两套价格口径，且可绕过日限（实际刷灵石口）**
   - 详情页按钮显示 `sellPrice(it.t)`（6720、6735），但点击后走 `eatItem(curIdx,'sell')`（6760），而该分支用的是**固定价** `ITEMS[it.t].sell`（6666-6671）。
   - 材料固定价见 5545-5574（如 `boss_heart: 10000`、`mat_marrow: 25000`）；坊市实际价是 `needOf(rank) * SELL_K * sellRate`（5778-5783）。
   - 后果：① 显示的价与实收价可能完全不同（低境界固定价更高、高境界固定价更低）；② 该分支**不递增 `S.market.sold`、不看 `sellRate`、不触发超额压价**，直接绕过第 5777 行注释所述的"防无限刷灵石"日限；③ 新丹药 `ITEMS` 条目没有 `sell` 字段（918-927 只写 `SELL_K`），所以丹药品详情会显示"寄售 N 灵石"但点击提示"无法寄售"，是假按钮。
2. **`addItem` 返回值被多处理忽略**：签到（1973-1974）与任务（8413-8415）在背包满时仍推进签到天数/任务完成标记，奖励静默消失。
3. **调试接口全局可达**：`const XX` 是顶层脚本绑定，且 `_s: S`（11841）、`_applySaveText`（11885）、`_equipItem`（11888）等都在其中。它不是隐藏后门，但对"同页脚本可任意改资产"没有防线；一旦叠加第 8 项的存档 XSS，攻击面会放大。

---

## 总体结论（Qoder）

**"负资产"**：未发现真实路径。`removeItems` 静默但不会扣成负数；`matTake` 的裸减法只在所有调用点前置校验、且配方无重复材料的条件下安全，属于潜在脆弱点。

**"越权扩容"**：常规玩法未发现。`bagSize` 读档/购买/兑换全部封顶 50，洞天加成有等级钳制，所有直接写包路径都有容量检查；唯一无检查的转世回收是设计明示的超容。

**"可被刷取"**：存在，但重心不在"容量/扣减"，而在**经济口径与存档面**：
- 真正可操作的刷取口是**详情页按固定价寄售，绕开坊市日限、行情与已售计数**；
- 存档/导入无签名，可复制物品、把装备与灵兽填到服务器上限；同时 `bag[].n` 未转义，构成持久 XSS；
- 联机端不持有背包，物品永不参与服务器对账，"背包服务器权威"不成立，但在当前物品不跨玩家的设计下属既定边界。

### Top 3 必须修

1. **【高】存档 `bag[].n` 直接进 innerHTML 的持久 XSS，以及读档不对 `t/n` 做白名单**
   - 位置：4341、10956、10959、5878、6722。
   - 修法：渲染一律 `escHTML(it.n)`（或只用 `ITEMS[t].n` 覆盖显示名）；读档改为 `typeof x.t === 'string' && Object.prototype.hasOwnProperty.call(ITEMS, x.t)`，并丢弃/重建未知 `n`。
2. **【中】详情页寄售固定价绕过坊市日限 / 行情，且展示价与实收不一致**
   - 位置：6665-6679 对比 5778-5797；按钮 6735/6760。
   - 修法：详情页寄售统一走 `sellMarket`/`sellPrice`；或删除 `force === 'sell'` 的固定价分支，只保留坊市一条成交口径。顺带修复丹药"显示可卖但点了不能卖"。
3. **【中】`equipItem` 超容时先 splice 再 addItem，导致旧装备永久丢失**
   - 位置：5974-5984；合法触发条件：转世 8513-8539 或改奉主洞后容量收缩。
   - 修法：先确认换下的旧装备能入库（或超容时直接拒绝换装），成功后再 `splice` 与写槽；与 `unequipItem`（6002-6006）的顺序保持一致。

> 补充建议（非 Top 3）：把 `removeItems` 改为返回实际删除数、`matTake` 对计数器做 `Math.max(0, ...)` 兜底；所有 `addItem` 调用检查返回值，避免满包静默丢奖。
