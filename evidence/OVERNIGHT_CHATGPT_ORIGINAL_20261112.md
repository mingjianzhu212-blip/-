1.2 候选 A 的核心问题

combatPower() 不只是战斗攻击力计算工具。

按照本单提供的事实：

pMax 取自 combatPower()。

pHP 使用 pMax。

powRatio 使用 pMax。

其他系统也使用 combatPower()。

multiPower() 还存在联机入口。

因此，把道途乘子加入 combatPower()，实际修改的不是一个局部战斗参数，而是全局战力语义。

会产生三个实质性问题。

第一，生命值连带放大。

如果道途加成进入 combatPower()，而 pMax 继续取其结果，那么道途加成可能改变玩家最大生命值。

这不是单纯攻击加成。

第二，战斗以外的系统也可能受影响。

例如门槛判断、塔、秘境、击杀时间估算以及其他依赖战力的系统。

即使这些系统原本不打算接受道途加成，也可能因为共用函数而发生变化。

第三，联机计算边界被污染。

multiPower() 的调用链需要重新检查，不能仅凭单机设计意图保证联机完全不受影响。

所以 A 不符合本轮要求的局部接线原则。

1.3 候选 B 的优势及必要限制

B 的优势在于把道途加成从全局战力体系中分离出来。

但必须明确：

不能因为 openBattleAnim() 是统一入口，就在入口直接修改所有战斗数值。

因为该函数同时承担 script 与非 script 两种战斗。

建议采用以下设计约束：

pathBonus 仅为本场非 script 战斗的独立上下文数据。

script 战斗不得读取或应用该加成。

只有玩家攻击的最终伤害计算分支可以应用加成。

mobTurn() 玩家受击计算不应用。

不改变 pMax、pHP、powRatio。

不改变 combatPower()。

不改变 multiPower() 和服务器共鸣计算。

不改变奖励结算。

还必须区分两个概念：

一次攻击计算只应用一次乘子。

一场战斗可以有多次玩家攻击。

如果批准公式规定每次玩家攻击都享有道途加成，那么每次攻击都应独立应用一次，而不是整场战斗只加成一次。

不能将这两个概念混为一谈。

2.2 A：新增 S.path
ChatGPT 首选推荐

存档语义：

道途作为单机角色状态的一部分。

随主存档一起保存。

角色恢复时一起恢复。

老存档没有该字段时安全初始化。

非法值不得污染角色存档。

重置角色时遵循既有主存档重置语义。

优势：

单机道途属于角色成长或角色配置时，放入主存档是最自然的归属。

不需要依赖联网，不需要将联机偏好解释成单机权威状态。

主要风险：

必须确认主存档默认值和迁移策略。

必须检查保存、加载、重置是否保持一致。

不能因为新增字段就改变其他存档字段的恢复语义。

必须考虑旧版本存档和异常值。

我认为这是最符合单机游戏长期维护的方案。

2.3 B：复用 MULTI_PATH_KEY

现有注释已经明确：

MULTI_PATH_KEY='jxwd_multi_path_v1'

不进入主存档。

因此它更接近独立的联机偏好或配置状态，而不是单机角色权威状态。

优势：

不需要直接改变主存档 schema。

可以独立读取和保存。

离线环境下，如果浏览器本地数据存在，仍然可以读取。

主要风险：

联机道途和单机道途可能不是同一个概念。

用户切换账号可能发生数据串用。

联机选择与单机成长可能发生冲突。

清除联机数据时可能意外清除单机状态，反之亦然。

本地键损坏或不存在时，无法保证单机角色状态正确恢复。

尤其不能因为键名中包含 PATH，就认定它可以直接作为单机权威数据源。

我的意见：不推荐直接复用。

除非只读核实证明它实际上具有完全相同的语义、作用域及生命周期，否则不应混用。

2.4 C：服务器档案权威

存档语义：

服务器保存道途状态。

客户端读取服务器权威状态。

客户端不能自行决定最终道途。

优势：

可以统一管理联机角色状态。

能避免客户端随意修改权威数据。

但本轮目标是单机道途。

问题在于：

离线不能保证读取。

新角色或服务器不可用时存在初始化问题。

会把单机玩法绑定到联机账户体系。

容易与现有生产共鸣计算形成语义耦合。

可能扩大本轮服务器修改范围。

而本轮禁止修改：

server/server.mjs

server/profile.mjs

因此不适合拿服务器档案作为单机道途权威来源。

我的意见：不推荐。

3.2 什么才算消除并行抖动污染？

我建议采用以下验收定义。

第一阶段：执行环境隔离。

关闭并行测试任务。

确认没有遗留测试进程。

确认端口没有被其他项目占用。

确认测试进程之间不会共享冲突的临时端口。

确认测试结束后端口释放。

第二阶段：串行回归。

在同一代码版本、同一测试环境、同一命令下执行全树回归。

建议连续执行三轮。

三轮之间不修改代码、不更换测试配置、不引入其他并行工作。

第三阶段：结果一致性。

三轮必须满足：

测试总数一致。

失败集合一致。

不出现新的端口冲突。

不出现新的偶发超时。

不出现跨测试数据污染。

不出现进程残留。

预期结果应以稳定基线为准，而不是机械要求 0 失败。

例如，如果改前已明确存在 3 项 D-008 失败，那么不能把这 3 项偷偷算作本轮端口变更导致的回归，也不能宣称全绿。

还要区分：

网络临时不可用。

这些情况不能全部处理成同一种数据清理操作。

尤其不应在登出时顺带删除无关的游戏存档和本地角色数据。
