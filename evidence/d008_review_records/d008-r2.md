## 二、关于 `ok` 字段的设计判定（回应第一轮 #3）

第一轮指出「注释宣称每个选项都有 label/fx/ok，但校验器未检查 ok」。本轮落实 ok 检查，但做了**语义精确化**而非盲目全量强制，依据如下真实引擎证据：

- `js/game.js` `resolveEncounter`（约 5314-5338 行）：
  ```js
  let detail = o.ok || '';                       // 缺省 ok 由引擎兜底为空串
  if(o.fx && o.fx.roll && o.fx.roll.length){
    ...
    detail = hit.text || '';                     // roll 选项：detail 被分支 text 覆盖
  }
  if(detail) log('📖 ' + detail, 'sys');
  ```
- 结论：**`ok` 只对「非 roll 选项」实际展示**；对 roll 选项，`ok` 是被分支 text 覆盖的死数据。
- 因此契约只在「非 roll 选项」上强制 `ok`；roll 选项的 `ok` 不强制（避免校验造绿、且与引擎真实行为一致）。
- 既有 4 条（`beggar/pouch/stele/amulet`）受红线「逐字未改」保护，且引擎对缺省 `ok` 有兜底（`o.ok || ''`），一并**祖父化豁免** ok 检查。
- 经全表扫描（`ORIG_ENC_IDS.indexOf(id)<0 && !(o.fx&&o.fx.roll)` 之外的选项）确认：30 条新增中仅 2 条 roll 选项（pouch_again#0、stele_again#0）无 ok，已被上述规则豁免；**所有新增非 roll 选项均带 ok**。

此判定未放宽对任何「会被展示」内容的约束——它把校验精确地对齐到引擎真实展示路径，比「所有 opt 必须有 ok」更严格地守住了玩家可见叙事的完整性。

      chkFx(o.fx);
    });

  L('encStructMeta', meta);
  L('encStructHtml', html);
  L('encStructBadKey', badKey);
  L('encStructBadRoll', badRoll);
  L('encStructBadTier', badTier);
  L('encStructBadShape', badShape);
  L('encStructOrig4', ['beggar','pouch','stele','amulet'].every(k => !!XX._encounters[k]) ? 'yes' : 'no');
})();
