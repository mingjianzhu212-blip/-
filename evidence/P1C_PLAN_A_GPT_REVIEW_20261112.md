3. 联机回写：服务器返回值能否覆盖 S.path？
当前设计必须修改

这是本件最重要的数据语义问题。

设计同时规定：

S.path 是玩家终身伴随的主存档本源；

不提供洗点或转职；

这三条并不天然兼容。

例如：玩家本地已选择 body，服务器却返回 sword。当前代码会静默覆盖本地终身道途。无论服务器值为什么不同，这都相当于绕过了已经确定的角色选择。

建议改为明确的冲突处理，而不是无条件覆盖：

本地 S.path 为空：可以考虑用服务器返回值补全，但必须确认这是允许的初始化来源。

本地与服务器均有效但不一致：登记冲突并停止自动覆盖，交由既定的数据一致性规则处理。

本地和服务器一致：正常同步缓存。

5. 注入点 B：script 分支是否严格不求值新乘子？
当前代码骨架与声明不一致

你给出的结构是：

JavaScript
const pathBonus = pathBonusFor(S.path);

const raw = script
  ? mMax / (script.win ? script.rounds : script.rounds + 2)
  : mMax * (0.26 + Math.random() * 0.08)
      * Math.max(1, Math.pow(powRatio, 1.3))
      * pathBonus;

JavaScript 的条件运算符确实只计算被选中的分支。因此，script 为真时，raw 的非 script 乘法分支不会执行。

但这里有一个细节：pathBonusFor(S.path) 已经在条件运算符之前执行了。

所以：

script 伤害数值不会乘上道途加成；

但 script 战斗仍然会执行道途加成的取值函数。

如果设计要求的是“script 不受加成”，当前表达式数值上满足；如果要求的是“script 分支完全不求值新乘子”，则不满足。

建议将计算改成：

JavaScript
const pathBonus = script ? 1 : pathBonusFor(S.path);

或者把取值放在非 script 分支内部。这样既保持普通战斗的战斗常量，又真正避免 script 场调用新取值逻辑。

我倾向第一种，改动最小、易读、容易测试。

此外，必须核实 script 在这段代码中确实已经完成判定，并且在整场战斗期间不会被意外改变。

6. 白名单兜底：PATH_IDS.indexOf() 是否足够？
校验方式认可

在 PATH_IDS 是固定、可信的字符串数组时：

typeof o.path === 'string' && PATH_IDS.indexOf(o.path) >= 0

已经能够拒绝：

null、undefined；

数字、数组、对象；

任意未知字符串；

__proto__、constructor、prototype 等不在白名单内的字符串。

这里不需要额外增加 Object.prototype 防护。因为代码并没有把存档对象的键展开或合并到原型对象中，只是在做字符串成员匹配。

它应作为固定常量使用，最好冻结，避免运行时被意外修改。

二、另外发现的两个施工设计矛盾

这两项不在七问中，但会直接影响实施正确性。

A. multiLoadPath() 的缓存回退与“补选”规则冲突

当前设计：

JavaScript
function multiLoadPath(){
  if (typeof S.path === 'string' && PATH_IDS.indexOf(S.path) >= 0) return S.path;
  try {
    const v = localStorage.getItem(MULTI_PATH_KEY);
    if (v) return v;
  } catch(e){}
  return 'sword';
}

问题在于：S.path === '' 被明确规定为“未选”，但这里会继续读取旧缓存，甚至最终默认返回 sword。

这可能导致：

老档明明需要补选，却在联机界面被显示成已有道途；

缓存中有脏字符串时返回非法值；

S.path 为空时，联机显示值与主存档本源不一致。

建议：multiLoadPath() 只返回经过白名单验证的 S.path，未选时返回 ''。

如果确实需要兼容旧缓存，应设计一次性迁移：只在 S.path 缺失、缓存值合法、且没有其他冲突时迁移到 S.path 并保存。不能每次读取时都让缓存覆盖本源。
