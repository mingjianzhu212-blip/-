## Muse 回复原文

═══ Q1 · A/B 对比与推荐：推荐 B ═══

影响面：A 并入 combatPower() 即改其全部约 40 处调用的语义（任务判定、面板、killTime、论剑秘境门槛、multiPower() 联机入口），等于重定义「战力」一词；B 只动非 script 的 playerTurn() 伤害公式一处（10583），战力口径本身不变。
双重计入：A 有两处——pMax 同时是 powRatio 分子与玩家满血 pHP，乘子会连带放大血量；且联机 multiPower() 复用 combatPower()，客户端先乘一遍、服务器再按 SYNERGY_GAIN 算一遍，即双计。B 的 pathBonus 为开战时算定的局部常量、伤害公式里只乘一次，回合递归（10596/10623）不重算，天然单次。
联机口径：A 使客户端联机战力与服务器重算口径分叉（权威在服务器重算＋钳制，分叉只会制造钳制异常）；B 完全不经过联机路径，零污染。
验收可判定性：A 须对 40 处调用逐一证明「无意外变化」，矩阵不可穷尽；B 用既定 11 项矩阵即可逐项判定（固定输入比对伤害数值即可验单次生效）。
必答前置问题（两条，设计定稿前必须回答）：① B 案下明确「道途加成只加伤害、不加血量」——pMax/pHP 耦合由此绕开，但须写进设计定版，不许实施时默认。② pathBonus 的数值来源：客户端现「不持有系数」，而服务器 pathAxisScore 依赖档案轴投入——公式在客户端等价复刻、还是由服务器下发数值？此问与 D1 绑定，答不出则 B 只是形状对、数值无源。

═══ Q2 · D1 选项包（推荐 (b)，不代祝选定）═══

(a) 主存档新增 S.path：语义＝随档走的角色属性，导出/换设备跟随；离线完全可用；风险＝动存档结构，须迁移与脏值兜底，老档默认无道途，且从此单机/联机两处各存一份道途、口径需另行声明。
(b) 复用 MULTI_PATH_KEY：语义＝本机偏好，不随档；离线可用；零存档改动；隔离风险＝同设备换档共用一个道途，且该键现注释为「服务器登记值才是权威」，单机若以它为准须在设计中明示「单机认本机偏好、联机认服务器登记，两者互不覆盖」，防双权威误读。
(c) 服务器档案为权威：单一权威最干净；但单机离线不可用，与单机玩法离线可玩的底盘冲突，本轮排除（可作远期收敛方向登记）。
推荐 (b) 的理由：唯一不动存档、不破离线、改动面最小的选项；若祝更看重「道途是角色属性、应随档走」，则选 (a)，代价是多一轮存档迁移设计。选择留晨报一签，我方不自决。

═══ Q3 · 端口基建验收口径 ═══
上轮回滚的教训是拿绝对数字当标准（基线本就 276/3，又遇抖动 265/14，无从分辨谁是谁）。我方口径改为相对基线判定：

改前冻结基线：串行全树结果＋具名既有失败清单（D-008 契约 3 例逐个点名），此后所有比较对这份清单。
改后串行结果须与基线逐项一致（通过数相同、失败集合相同）。
并行稳定性：并行全树连跑 ≥5 次，每次结果集合与串行基线完全一致，且日志中端口冲突特征（EADDRINUSE 等）为 0——抖动是概率事件，单次全绿不算证据。
出现清单外新失败即不验收，不因「总数差不多」放行；既有 3 例失败不在本变更内顺手修，另行登记。
端口分配须按测试文件确定性映射（固定表或文件名哈希），禁用 pid 派生的重叠段。

═══ Q4 · K11 与 token ═══

K11 威胁模型最小集：同挂单并发双买（双花）、同 _idem 键重放（重复结算）、cancel 与 buy 竞态、转移中途崩溃（借贷不原子→资产创生/湮灭）、数量边界（0/负数/超栈）、自买自卖、越权 token 调用。测试矩阵最小集：以上每类一例＋一条不变量贯穿——任意操作序列后全服资产总量守恒、任一资产恰属一人、同一挂单至多成交一次；随机操作序列循环跑守恒断言一条，胜过堆十条静态用例。另：transfer() 整栈转移既定设计已由 K11-15 坐实，设计稿不得再按「部分转移缺陷」立项。
token 三要素关键风险：存储介质——localStorage 持久但可被注入脚本读走，本游戏全量 innerHTML 重绘、文本注入面真实存在，此风险须在设计稿中正面写明而非回避；登出清理——只清本地键挡不住已复制 token，服务器侧会话失效缺位须登记为已知缺口；过期回退——失效 token 续接被拒后必须清键并回退全新连接，且防「拿着死 token 无限重试」的循环，另注意多标签页同写一键的竞态。
